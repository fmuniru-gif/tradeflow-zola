## Root causes and implementation

1. The protective directory hold returns before cloud-client initialization. The generic capability check then reports `CLOUD_CONFIGURATION_REQUIRED` for a null client, even when saved configuration is present. Shop now displays a distinct recovery hold; actual configuration, authentication and lifecycle failures remain blocking.
2. Existing Main quarantine and Camon preservation are identity-specific and unsuitable for Shop. This implementation validates the precise Shop identity, local staff Owner, authenticated cloud Owner, business, ACTIVE lifecycle and canonical access; explicit revocation overrides historical registration fallback.
3. Real staff login mirrors login timestamps into the synchronized staff directory. Shop alone skips this mirror while held, allowing local login audit without regenerating directory publications. Healthy devices retain the original path.

The queued root is the whole **staff authorization directory**, including roles, activation flags and salted password verifiers. It is not a hardware registration directory. Each operation must have one `root-set` patch, correct predecessor chain, M4/3 identity, deterministic payload hash and increasing device sequence. Added/removed staff, changed roles, credentials and reactivation differences are counted for Owner review; they are never automatically declared harmless. A visible matching cloud operation is reported with its server cursor; absence is explicitly inconclusive about pre-checkpoint history.

### Corrective disposition gate

Each operation now reports its actual **before → value** additions, removals, credential/role/profile changes, activations/deactivations, directory-enabled changes and timestamps, separately from its differences against current cloud authorization. No staff names, IDs or verifiers are displayed. Quarantine is forbidden if any operation has an unresolved consequential change; the general exact-ID confirmation cannot override it.

A safe operation must either have authorization content already reflected in the current verified cloud directory, or be timestamp-only residue whose supersession is positively proved. A newer cloud timestamp alone is insufficient for conflicting authorization content: the verified ordered cloud tail must demonstrate a matching directory transition to the current state. Only `updatedAt` and `lastLoginAt` are treated as volatile directory metadata; creation/credential-change timestamps, membership, roles, credentials, enabled and active flags are substantive. Ambiguity blocks quarantine. Saving a backup remains available for a blocked queue; saving is not permission to quarantine.

All Shop uploads, direct last-hop pushes, directory publications, ordinary cloud pulls/bootstrap replacement and synchronized local posting remain blocked. Normal authentication callbacks, online/focus events and reload do not release the hold. The queued operations are never uploaded, acknowledged, relabelled or marked applied by quarantine. There is no Live Sync release control in this candidate.

## Evidence, storage and interruption safeguards

The read-only preflight uses the existing stored authenticated Owner token without refreshing it or changing the SDK session. Network methods are GET plus only the existing read-only checkpoint and canonical-fleet RPCs. It brackets paginated ordered operations with identical checkpoint/head/lifecycle/fleet/master metadata and accepted-operation lookups. Production checkpoint hashes, operation hashes and the actual integrity projector are checked. Missing authority, expired session, moving head, unsupported schema or replay conflict stops the procedure.

The V2 externally saved full backup is AES-256-GCM with random salt/IV and PBKDF2-SHA256 (600,000 iterations), bound to Shop. It contains the complete original DB, sync state, original queue and applied-operation register, failed/apply metadata, current authoritative staff directory and classifications, with SHA-256 manifests for original bytes and the entire sealed full-state bundle. Before receive, a **fresh externally saved/readback-verified backup** additionally includes its current before-state and exact proposed target. It retains the complete original baseline. Keep both verified files. A queue-only V1 archive cannot satisfy this gate. The file is reopened from its saved handle, byte-compared, authenticated-decrypted and content-compared before mutation is possible. Staff password verifiers exist only inside the encrypted file. Passphrase is never persisted; unsupported saved-file readback blocks recovery.

Supabase session storage is never read for backup. Plaintext credential/PIN/public-key fields within DB/state are replaced with byte-preserving credential slots and hashes, **inside encryption**. Restoration reuses only identical credential values still present locally; missing/changed retained values produce `RETAINED_CREDENTIAL_REQUIRED`. Credentials are never invented, reset or exported in plaintext. The backup independently contains all original non-credential business/state values; this is not permission to migrate a device identity to another live browser or reset site data. Local journal interruption recovery remains, and a missing/damaged journal now has the explicit external restoration path below.

For an independent reader, the V2 envelope records base64 salt, IV and ciphertext (including GCM tag); derive a 256-bit AES key from UTF-8 passphrase using its specified PBKDF2 parameters. Authenticated additional data is the literal `ZEZMS_SHOP_DIRECTORY_V1|197e3568-5a89-4a56-b9d0-07f5e8248734` (the identity binding is retained while the payload/envelope version becomes V2). Decrypted `fullState.original/point/target` contain the six named storage snapshots as exact JSON byte-template pieces, per-snapshot SHA-256s, and credential-slot paths/hashes. Joining string pieces and substituting null for credential slots yields an independently readable credential-redacted DB/state. Restoration resolves each slot only from a matching unchanged local credential slice, preserving original JSON bytes and verifying original SHA-256. The whole sealed bundle and classification are also SHA-256 verified using the canonical sorted-key serialization in the reviewed core. No local journal is required to authenticate/decrypt/read this file.

Before the first journal write and before receive commits, an actual localStorage capacity probe calculates the serialized full proposed journal/before/target budget, including JSON escaping, complete register copies, current projected DB/register growth and a 64 KiB margin. It reserves the additional capacity required beyond the journal already allocated, then removes only its dedicated scratch key. Failure leaves operational keys untouched. It is a transient, Owner-confirmed scratch write at the mutation boundary; the read-only preflights do not write. Capacity is rechecked at each phase because the cloud can grow. Storage can still fail later, so prepared journal and external backup recovery remain mandatory. This test is stronger than a browser-wide origin quota estimate, but deliberately conservative and may require more headroom than the final journal uses.

Journal writes and readbacks precede queue removal. Storage/quota failures leave the original queue or a documented resumable phase. Prepared receive targets are independently rederived from authenticated cloud data before resumed writes. Interruption never starts automatic upload or automatic resume. Reimport and decrypt the saved archive after reload before any further mutation. Other windows, an old worker, missing worker attestation or uncontrolled tabs block mutations.

## Receive-only proof

Receive is a separate Owner confirmation after quarantine. It requires an empty queue and independently verified archive, fresh stable authority and a checkpoint at or before Shop's cursor. A checkpoint newer than Shop is a blocker, not permission to overwrite the local DB.

The actual production integrity engine reconstructs cloud state at Shop's cursor and at the latest head. Every synchronized collection and root is compared, including financial balances, management/KPI roots and settings. Only explicitly local-only fields and the existing production-derived `undoLog.productId` metadata normalization are excluded. Unexpected business differences stop recovery. The only permitted pre-replay discrepancy is the preserved directory root, which must match the last archived publication or the cloud root at that cursor.

Replay uses a clone of Shop's DB with the cloud directory at its verified cursor, preserving local-only settings/authentication. Candidate and cloud current synchronized states must agree; stock, finite wallet amounts and production cash constraints are checked. Historical orphan references must match the cloud's own references and are separately reported, never deleted. Only actual received tail operations get applied-register entries; historical register gaps are untouched.

Post-commit Cloud-vs-Local verification requires current head equality, empty outbox, no ordinary missing/mismatched/duplicate records or unapplied tail, matching wallets and unchanged identity. New cloud activity requires a fresh receive preflight; it never justifies stale acceptance.

### Failure and rollback

- Stop on any `SHOP_STOP_*` result. Do not reconnect an unquarantined queue through an older shell or run generic repair/clear/reset tools.
- Interrupted quarantine: stay offline, keep the reviewed single-tab worker, reimport/verify archive after reload and repeat the exact-three action. It accepts only known original/empty queue states.
- Interrupted receive: reimport/verify archive and choose **Resume interrupted receive only**. Pinned authority must still match. If cloud moved or later local data exists, stop; do not force a retry or discard data.
- To undo this recovery, go fully offline, keep one reviewed tab, verify the original archive, and explicitly choose **Restore preserved local state (offline)**. It restores only known original DB/register/state/queue snapshots, with upload/live flags held. Later unrelated DB/register/queue changes block rollback. Retrying interrupted rollback is safe.
- Missing/damaged journal: remain fully offline, close all other tabs and use the latest verified V2 full backup through **Verify saved archive**, then separately approve **Restore verified external backup — lost journal (offline)**. It authenticates/decrypts the file, verifies original bytes and retained credentials, checks current device/Owner/business and that DB/state/queue/register are known original/before/target values, then reconstructs a durable rollback journal and restores the original business state. Unknown later business data stops restoration. The damaged journal is retained locally inside the reconstructed journal for audit. This path does not call cloud APIs or require manual DB editing. Interrupted restoration resumes through the same control after re-verifying the file.
- Legitimate device-local authentication audit, backup/sync metadata and version fields are compared separately and retained from the current device during rollback. They are not evidence of a synchronized business difference. Every other DB field remains checked, including unknown top-level fields; changed synchronized cash, records, settings or directory data cannot be hidden as local metadata.
- Only the derived sync-state display fields `status` and `pending` may differ on reload for external restoration/resume. Cursor, device sequence, Owner/business/device identity, live flags and other synchronization state must match known original/before/target states. This is not a cursor reset or register repair.
- A deployment rollback is not a data rollback. Keep Shop offline during any code rollback. Do not open the old production shell online with a restored queue or an empty quarantined queue: older code does not understand this Shop journal. Retain a guard-bearing shell until an independently reviewed successor preserves the hold. Main and other devices require no local data restoration.
