# Sync resilience, A5 watermark and desktop presentation

Baseline: production `5ffe6f432712efc170e86e7710806881953a50f4`. Delivery: `20261103-sync-resilience-performance-r1`.

A5 receipt, invoice, waybill and quotation PDFs draw the watermark over the full 419.53 × 595.28 point page. Landscape A5 is also supported. Receipt/commercial system/direct-print HTML uses a 148 × 210 mm watermark with independent horizontal and vertical scaling. The watermark stays at 10% opacity; the header seal remains proportionate. A4 PDF placement remains unchanged. A printer's physical non-printable margins can still clip the outer edge; no physical printer was available for this review.

## Operation reliability

The shared operation uploader now uses a 15-second deadline for each request and at most three send attempts, with bounded exponential backoff and jitter. It never generates a replacement operation ID. After a transient POST failure it reads back the exact operation before considering another POST, checking its sequence, identity and recomputed complete payload hash. A committed operation with a lost response can therefore be acknowledged without another send. A successful POST with unavailable read-back remains unresolved; it cannot clear the queue. Stock/cash conflicts, identity/hash failures and authorization errors are not automatically retried. Changed owner/device context prevents acknowledgement, and paused live sync prevents another automatic send within a retry sequence.

Operation-page, Cloud-master and checkpoint reads have request deadlines and at most three attempts for transient network/server failures. Downloaded pages must have strictly increasing positive safe-integer sequences, unique nonempty operation IDs, object payloads and consistent row/payload identities. A repeated second page fails before local rebase or cursor advancement. Sequence gaps are allowed because server sequence numbers can span owners. Existing capability checks, account ownership filters, recovery holds, cursor/application journals, FIFO, business calculations and conflict compensation remain authoritative. This release does not migrate or modify Supabase. Server configuration, connectivity and physical-device convergence are not established by synthetic tests.

Stock-correction replay validates stable patch identity before the duplicate-event guard. The same correction ID must have identical immutable event data, including quantity, cost, product and allocations. Reversal lifecycle fields may differ. An altered event stops for review instead of silently being treated as an already-applied correction. Identical replay never reapplies its stock delta or erases subsequent stock movements.

## Desktop work

Cash history builds fresh first-match account/expense link indexes once per render rather than repeatedly scanning both collections for every displayed row. Sales, cash and account histories decorate dates once for sorting and reuse date-formatting machinery. Stock In reads only its last 30 rows and lazily constructs a fresh first-name-match product-ID index for historical rows lacking IDs. No financial models, stock quantities or formatted balances are cached between renders. Existing rows, sorting, permissions, action targets, totals, 50-row pagination and 100-row history bounds are retained.

The paired benchmark serves every baseline asset from its exact Git commit, blocks external requests and uses isolated synthetic Owner profiles: Main 4× CPU, Shop 2× CPU. It measures a first visit and seven warm visits to Sales Records, Stock In, Cash, Stock Balance, Accounts and Dashboard. Two animation frames measure a paint opportunity, not physical display latency. Complete view markup/action hashes and database/outbox snapshots must match baseline. Timing evidence is retained in CI log JSON. Stock In layout and native product selection still cost time; this change does not claim every route is now instant or prove speed on the operational laptops.

Local Main-style seven-sample medians before/after: Sales Records synchronous 47.1/35.5 ms, paint opportunity 124.6/114.6 ms; Cash synchronous 57.8/31.4 ms, paint 177.2/146.4 ms. Stock In paint was essentially unchanged at 133.3/133.8 ms. Accounts paint was 261.5/245.5 ms; unchanged Dashboard control varied from 80.7 to 103.0 ms. These are synthetic observations, not physical-device guarantees; dedicated CI repeats both profiles.

## Delivery and validation

All original embedded module bytes and pre-existing standalone business/protocol scripts remain unchanged. Exact asserted transformations apply to the verified assembled delivery; a whole-output equality test proves that only those reviewed edits and the two injected helpers differ. The approved document-branding helper receives the A5 matrix change. The passive offline delivery pins 84 assets and retains prior caches and device data.

Fault injection covers lost acknowledgements, failure before commit, exhausted network/read-back attempts, aborts, changed context, permanent conflicts, forged hashes, malformed/repeated pages, correction replay, reversal and ID reuse. Browser tests use the real correction builder/replay engine across two isolated devices and the pinned Supabase 2.112.1 SDK against synthetic HTTP responses. All eight PDF types plus a four-page invoice are exported offline and rendered for visual inspection. Full source/unit, browser, cached-upgrade, recovery-hold and synthetic data-preservation regressions run in a loopback-only network namespace. No live stock/cash adjustment or operational-device recovery is part of this release.
