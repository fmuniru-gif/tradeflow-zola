## Evidence and limits

Automated tests run the **assembled shell** in an isolated Chrome profile with all nonlocal network requests blocked. The synthetic fresh-browser startup produced one `DATABASE_CHANGE` with `insert kpiHistory` and `root-set settings`, classified `UNKNOWN / REVIEW REQUIRED`. The `js/confirmed-july-snapshot.js` `run()` handler waits for cloud readiness, then calls `saveDB()` when its confirmed July record is absent; its guard checks Phase A pending, not M5A-4 staged-candidate state. On a new browser this occurs before the test installs the verified stage and creates the KPI patch. A settings root change is in the same save diff. `js/auto-month-rollover.js` also initializes a model and may save or perform a month rollover on startup/focus/cloud-ready; staff recovery and other setup code have save paths. Their exact effect on **Camon 17P** is unknown. An insert in `kpiHistory` is a business patch, and a `settings` root is safe only if byte-for-byte candidate-equivalent. No blanket cleanup is justified.

The browser tests also substitute a single exact candidate-equivalent settings patch, a sales insert, and a mismatched settings patch. The classifier reports respectively SAFE_SETUP_RESIDUE, BUSINESS_OPERATION, and UNKNOWN / REVIEW REQUIRED. In each case inspection plus JSON download preserves the entire localStorage snapshot, database, device state, cursor, stage, journal, and queue; no RPC, activation, or external request occurs during the click. Existing r70U staff-login tests still exercise actual staff authentication and recovery modules. These are synthetic tests, **not evidence of Camon 17P's actual queue**.
