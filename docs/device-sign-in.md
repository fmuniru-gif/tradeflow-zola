# Optional device sign-in — 20261108-device-sign-in-r1

This adds **local staff sign-in with a platform passkey** alongside the existing password. It uses the same device-local staff authentication boundary that already verifies PBKDF2 staff passwords. It does not implement Supabase/Cloud passkey authentication, issue Cloud tokens, replace Owner MFA, enroll a device or release any recovery hold. Local storage/profile integrity is still part of the existing local-staff trust model; this is not a new remotely authoritative identity service.

## Using it

On each active registered device/browser, sign in normally and open **Device sign-in** in the sidebar. Confirm that the OS profile/device unlock is private to the current staff member, re-enter that staff password and approve the OS/browser fingerprint, face or PIN prompt. At the next login, select the same staff member and choose **Sign in with device · fingerprint / PIN**. Password login always remains available. Platform capability is detected; unsupported browsers retain password login. Setup is separate on each browser/device. Removing the local registration requires the staff password; it disables TradeFlow's alternative but does not delete a leftover credential from the OS credential manager.

**Shared OS profiles are not separate staff identities.** WebAuthn verifies that someone can unlock the OS/browser credential; it does not tell TradeFlow whose enrolled fingerprint was used. Anyone who can unlock that same OS profile may use its passkeys. Use separate private OS profiles for staff on shared computers. TradeFlow cannot detect or enforce which fingerprint/PIN the OS accepts, or promise fingerprint-only verification. Raw biometrics are never requested, stored or transmitted by TradeFlow. An OS/browser credential manager may manage/sync its credentials independently; TradeFlow's registration metadata is local to this browser and device binding.

## Verification and lifecycle

After native staff-password reauthentication, enrollment requires a platform ES256 credential, fresh 32-byte challenge, matching create type/origin/RP hash, user presence and user verification, and a matching attested credential ID. Browser Level 2 public-key/authenticator-data methods avoid a custom CBOR decoder. Authentication validates fresh single-use in-memory get challenges, exact origin/RP, selected staff/credential/user handle, required UP/UV flags, backup eligibility, monotonic positive signature counters (zero-counter authenticators remain supported), and the complete WebCrypto P-256/SHA-256 signature. Strict DER-to-P1363 conversion handles the signature representation; no custom cryptographic algorithm is used.

Metadata includes only credential ID/public key, opaque random handle, counters, and hashes binding the active staff verifier/role/business and the established device/profile/app scope. It is stored separately from DB/business backups/outbox, never a reusable password/private key. Native password failures retain their existing lockout behavior, and lockouts also block device login. Live and durable staff snapshots must agree. Changed password/role, disabled/deleted staff, different device/tenant/Owner binding, startup/recovery holds, stale responses and cancellation block the alternative. Offline revocation cannot be known before the cached directory/device state receives it, the same limit as existing offline staff passwords.

Web Locks serialize credential operations across tabs. Close, hide/page exit, staff switching, logout and changed local state cancel pending ceremonies. Registration changes/storage failures cannot grant sign-in. The private native success path is shared by password and verified-device sign-in; it sets the same roles, clears privileged flags/cart, writes the ordinary staff audit (device method labeled LOCAL_DEVICE_PASSKEY), and starts the existing five-minute idle controller. Cloud MFA/PIN rules remain separate. No existing business posting source is changed.

## Validation and limits

Unit tests use real P-256 signatures and malformed/replayed/wrong-origin cases. Isolated Chrome tests use the real browser WebAuthn implementation with a virtual internal authenticator, real native password authentication, credential persistence, offline local sign-in, permission preservation, cancellation/revocation/storage failures and idle expiry. Synthetic business records and loopback-only networking keep all production data untouched. Physical fingerprint/Windows Hello enrollment must still be observed on each actual device; virtual tests cannot certify sensor availability or a credential manager's offline behavior. Password fallback is required for failures and recovery.
