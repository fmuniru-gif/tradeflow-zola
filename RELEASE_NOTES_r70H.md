# r70H — Existing ACTIVE Device Identity Relink

The affected Phone may have either an authenticated Owner session or its original authenticated anonymous PAIRED session while its local `deviceId` no longer matches. r70H treats both as local identity-pointer loss, not a new-device or restore case.

An anonymous session first calls the read-only `zezms_m5a4_my_active_device_binding()` resolver. It accepts no device/lifecycle input and proves only `auth.uid()`'s own ACTIVE access/lifecycle/registry binding. A valid result restores that same PAIRED pointer and session directly. If no valid self-binding exists, r70H shows **Verify Owner to identify this existing device** and only makes the Owner fleet-selection flow available after Owner MFA/AAL2 succeeds.

After explicit Owner selection and MFA/AAL2 server verification, r70H preserves the selected device's authoritative mode. OWNER mode retains (or deliberately adopts) the verified Owner session. PAIRED mode creates or reuses an exact anonymous session and atomically binds it to the same existing access, lifecycle and registry rows only when genuinely required. It then refreshes presence against that same row.

The phones remained shown as 3.31.4 because their browsers had drifted from the original device IDs, so their normal device-context calls no longer reached the original registered rows. Main and Shop continued updating because their local identities remained matched. The old M5A3 compatibility context accepted app-version input but discarded it when delegating to M5A4, while M5A4 refreshed only last-seen metadata. r70H makes the same validated M5A3 context perform the resolver-protected presence update after a verified, mode-consistent relink. It updates existing lifecycle, device-access and registered-device records—never duplicates.
